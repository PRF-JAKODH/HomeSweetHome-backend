커뮤니티 1차 성능 개선 ‐ 데드락 문제 해결

이 글에서는 커뮤니티 게시판의 좋아요/조회수 기능에서 발생한 **데드락(Deadlock) 문제**를 분석하고, JPQL 및 네이티브 쿼리를 도입하여 해결한 과정을 공유하고자 합니다.

---

## 기존 시스템 구조

커뮤니티 게시판에서는 게시글 조회수 증가, 좋아요 토글 기능이 있습니다. 기존에는 **비관적 락(PESSIMISTIC_WRITE)**을 사용하여 동시성을 제어했습니다.

### 기존 코드 구조

```java
// Repository - 비관적 락 사용
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT p FROM CommunityPostEntity p WHERE p.postId = :postId AND p.isDeleted = false")
Optional<CommunityPostEntity> findByPostIdAndIsDeletedFalseWithPessimisticLock(@Param("postId") Long postId);

// Service - 조회수 증가
@Transactional
public void increaseViewCount(Long postId) {
    CommunityPostEntity post = postRepository.findByPostIdAndIsDeletedFalseWithPessimisticLock(postId)
            .orElseThrow(() -> new CommunityException(ErrorCode.COMMUNITY_POST_NOT_FOUND));
    post.increaseViewCount();
}

// Service - 좋아요 토글
@Transactional
public void togglePostLike(Long postId, Long userId) {
    CommunityPostEntity post = postRepository.findByPostIdAndIsDeletedFalseWithPessimisticLock(postId)
            .orElseThrow(() -> new CommunityException(ErrorCode.COMMUNITY_POST_NOT_FOUND));
    User user = userRepository.findById(userId)
            .orElseThrow(() -> new CommunityException(ErrorCode.USER_NOT_FOUND));

    Optional<CommunityPostLikeEntity> existingLike = postLikeRepository.findByPostAndUser(post, user);

    if (existingLike.isPresent()) {
        postLikeRepository.delete(existingLike.get());
        post.decreaseLikeCount();
    } else {
        postLikeRepository.save(new CommunityPostLikeEntity(post, user));
        post.increaseLikeCount();
    }
}
```

## 문제 정의

### k6 부하 테스트 중 데드락 발생

k6를 활용한 부하 테스트 중 다음과 같은 에러가 빈번하게 발생했습니다:

```
Deadlock found when trying to get lock; try restarting transaction
```

### 데드락 발생 원인 분석

MySQL의 InnoDB에서 데드락이 발생한 근본적인 원인은 **S-LOCK → X-LOCK 업그레이드 과정**에서의 충돌이었습니다.

#### 1. SELECT FOR UPDATE의 락 획득 순서 문제

```
트랜잭션 A                          트랜잭션 B
─────────────────────────────────────────────────────────
1. SELECT ... FOR UPDATE (X-LOCK 대기)
                                    1. SELECT ... FOR UPDATE (X-LOCK 대기)
2. 게시글 row X-LOCK 획득
                                    2. 게시글 row X-LOCK 대기 (A가 보유)
3. 좋아요 테이블 INSERT 시도
   → FK 참조로 인해 posts 테이블 S-LOCK 필요
                                    3. 좋아요 테이블 INSERT 시도
                                       → FK 참조로 인해 posts 테이블 S-LOCK 필요
DEADLOCK 발생!
```

#### 2. FK 제약조건으로 인한 암묵적 락

좋아요 테이블(`community_post_likes`)이 게시글 테이블(`community_posts`)을 FK로 참조하고 있어, INSERT/DELETE 시 부모 테이블에 **암묵적으로 S-LOCK**이 걸립니다.

```
posts 테이블                    post_likes 테이블
┌─────────────┐                ┌─────────────────┐
│ post_id (PK)│◄───FK 참조────│ post_id (FK)    │
│ like_count  │                │ user_id (FK)    │
└─────────────┘                └─────────────────┘
      │
      ▼
INSERT/DELETE 시 posts 테이블에 S-LOCK 발생
```

#### 3. 락 획득 순서 불일치

| 시점 | 트랜잭션 A | 트랜잭션 B |
|------|-----------|-----------|
| T1 | posts X-LOCK 획득 | posts X-LOCK 대기 |
| T2 | post_likes INSERT → posts S-LOCK 필요 | - |
| T3 | - | posts X-LOCK 획득 |
| T4 | - | post_likes INSERT → posts S-LOCK 필요 |
| T5 | **DEADLOCK** | **DEADLOCK** |

## 해결 방안

### 핵심 아이디어

**"SELECT 후 UPDATE 하지 말고, 바로 UPDATE하자!"**

기존 방식은 `SELECT FOR UPDATE`로 엔티티를 조회한 후 필드를 수정하는 방식이었습니다. 이 과정에서 S-LOCK → X-LOCK 업그레이드가 발생했습니다.

**JPQL/네이티브 쿼리로 직접 UPDATE**하면 처음부터 X-LOCK만 획득하므로 데드락을 방지할 수 있습니다.

### 개선된 코드 구조

#### Repository 변경

```java
public interface CommunityPostRepository extends JpaRepository<CommunityPostEntity, Long> {

    // 기존: 비관적 락 사용 (제거됨)
    // @Lock(LockModeType.PESSIMISTIC_WRITE)
    // Optional<CommunityPostEntity> findByPostIdAndIsDeletedFalseWithPessimisticLock(...);

    // 개선: JPQL로 바로 UPDATE (S-LOCK 없이 X-LOCK만 획득)
    @Modifying(clearAutomatically = true, flushAutomatically = true)
    @Query("UPDATE CommunityPostEntity p SET p.viewCount = p.viewCount + 1 WHERE p.postId = :postId AND p.isDeleted = false")
    int incrementViewCount(@Param("postId") Long postId);

    @Modifying(clearAutomatically = true, flushAutomatically = true)
    @Query("UPDATE CommunityPostEntity p SET p.likeCount = p.likeCount + :delta WHERE p.postId = :postId AND p.isDeleted = false")
    int updateLikeCount(@Param("postId") Long postId, @Param("delta") int delta);
}

public interface CommunityPostLikeRepository extends JpaRepository<CommunityPostLikeEntity, Long> {

    // JPQL DELETE - S-LOCK 없이 바로 X-LOCK 획득
    @Modifying(clearAutomatically = true, flushAutomatically = true)
    @Query("DELETE FROM CommunityPostLikeEntity pl WHERE pl.post.postId = :postId AND pl.user.id = :userId")
    int deleteByPostIdAndUserId(@Param("postId") Long postId, @Param("userId") Long userId);
}
```

#### Service 변경

```java
@Service
@RequiredArgsConstructor
@Transactional(readOnly = true)
public class CommunityCountService {

    /**
     * 게시글 조회수 증가 (Atomic Query로 동시성 제어)
     * S-LOCK → X-LOCK 업그레이드 데드락 방지
     */
    @Transactional
    public void increaseViewCount(Long postId) {
        int updated = postRepository.incrementViewCount(postId);
        if (updated == 0) {
            throw new CommunityException(ErrorCode.COMMUNITY_POST_NOT_FOUND);
        }
    }

    /**
     * 게시글 좋아요 토글 (Atomic Query + Resource Ordering)
     * 부모 테이블(posts) 먼저 UPDATE → 자식 테이블(post_likes) INSERT/DELETE
     * FK S-LOCK 데드락 방지
     */
    @Transactional
    public void togglePostLike(Long postId, Long userId) {
        // 1. 좋아요 존재 여부 확인 (락 없이 읽기만)
        boolean exists = postLikeRepository.existsByPost_PostIdAndUser_Id(postId, userId);

        if (exists) {
            // 취소: 부모 먼저 UPDATE (X-LOCK) → 자식 DELETE
            int updated = postRepository.updateLikeCount(postId, -1);
            if (updated == 0) {
                throw new CommunityException(ErrorCode.COMMUNITY_POST_NOT_FOUND);
            }
            postLikeRepository.deleteByPostIdAndUserId(postId, userId);
        } else {
            // 추가: 부모 먼저 UPDATE (X-LOCK) → 자식 INSERT
            int updated = postRepository.updateLikeCount(postId, 1);
            if (updated == 0) {
                throw new CommunityException(ErrorCode.COMMUNITY_POST_NOT_FOUND);
            }
            // 엔티티 조회 및 좋아요 생성
            User user = userRepository.findById(userId)
                    .orElseThrow(() -> new CommunityException(ErrorCode.USER_NOT_FOUND));
            CommunityPostEntity post = postRepository.findByPostIdAndIsDeletedFalse(postId)
                    .orElseThrow(() -> new CommunityException(ErrorCode.COMMUNITY_POST_NOT_FOUND));

            postLikeRepository.save(new CommunityPostLikeEntity(post, user));
        }
    }
}
```

## 개선 포인트 정리

### 1. Atomic Query 도입

| 기존 방식 | 개선 방식 |
|----------|----------|
| SELECT FOR UPDATE → 엔티티 수정 → flush | JPQL UPDATE 한 번으로 처리 |
| S-LOCK → X-LOCK 업그레이드 발생 | 처음부터 X-LOCK만 획득 |
| 데드락 가능성 높음 | 데드락 가능성 제거 |

### 2. Resource Ordering (자원 순서화)

좋아요 토글 시 **항상 부모 테이블(posts)을 먼저 락**하고, 그 다음 자식 테이블(post_likes)을 처리합니다.

```
개선된 락 획득 순서:
1. posts 테이블 UPDATE (X-LOCK 획득)
2. post_likes 테이블 INSERT/DELETE

모든 트랜잭션이 동일한 순서로 락을 획득 → 데드락 방지
```

### 3. @Modifying 어노테이션 옵션

```java
@Modifying(clearAutomatically = true, flushAutomatically = true)
```

- `clearAutomatically = true`: 쿼리 실행 후 영속성 컨텍스트 초기화 (캐시된 데이터와 DB 불일치 방지)
- `flushAutomatically = true`: 쿼리 실행 전 영속성 컨텍스트 flush (변경사항 반영)

## 아직 남은 문제

데드락 문제는 해결되었지만, 여전히 다음과 같은 한계가 존재합니다:

1. **DB 부하**: 모든 조회수/좋아요 연산이 DB에 직접 쿼리됨
2. **트랜잭션 오버헤드**: 단순 카운터 증가에도 트랜잭션 필요
3. **확장성 한계**: 트래픽 증가 시 DB가 병목 지점이 될 가능성

이러한 문제들은 **[2차 성능 개선 (Redis 기반 카운터 시스템 구축)](커뮤니티-2차-성능-개선-‐-Redis-기반-카운터-시스템-구축)**에서 해결합니다.

## 마무리하며

이번 개선을 통해 단순히 "락을 걸면 동시성이 해결된다"는 생각이 잘못되었음을 깨달았습니다.

**핵심 교훈:**
- 비관적 락은 데드락의 원인이 될 수 있다
- SELECT 후 UPDATE보다 **Atomic UPDATE가 더 안전**하다
- FK 제약조건이 있는 테이블은 **락 획득 순서**를 고려해야 한다
- JPQL/네이티브 쿼리를 적절히 활용하면 JPA의 한계를 극복할 수 있다
