카운터 정합성과 동시성을 유지하며 성능 향상의 어려움

커뮤니티 **카운터 기능에 대해 ***정합성**, **동시성**, **성능** 요구사항을 동시에 해결하기 어려웠습니다.

이 글에서는 커뮤니티 성능 개선 과정에서 겪었던 **트레이드오프**와 **의사결정 과정**을 공유합니다.

---

## 카운터의 세 가지 요구사항

### 1. 정합성 (Consistency)
- 실제 좋아요 수와 저장된 값이 일치해야 함
- 데이터 유실이 없어야 함
- 서버 재시작 후에도 데이터가 보존되어야 함

### 2. 동시성 (Concurrency)
- 여러 사용자가 동시에 좋아요를 눌러도 정확한 값이 유지되어야 함
- Race Condition이 발생하지 않아야 함
- 데드락이 발생하지 않아야 함

### 3. 성능 (Performance)
- 빠른 응답 시간 (사용자 체감)
- 높은 처리량 (동시 요청 처리)
- 시스템 리소스 효율적 사용

---

## 트레이드오프: 세 가지를 동시에 만족시키기 어려운 이유

```
        정합성
         /\
        /  \
       /    \
      /      \
     /________\
  동시성        성능

세 꼭짓점을 모두 만족시키는 것은 매우 어렵다!
```

### 각 조합의 문제점

| 선택 | 희생 | 문제점 |
|------|------|--------|
| 정합성 + 동시성 | 성능 | 강한 락 사용 → 응답 지연, 처리량 저하 |
| 정합성 + 성능 | 동시성 | 락 없이 처리 → Race Condition 발생 |
| 동시성 + 성능 | 정합성 | 메모리 캐시만 사용 → 데이터 유실 가능 |

## 시도 1: 비관적 락 (PESSIMISTIC_WRITE)

### 접근 방식
```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
@Query("SELECT p FROM CommunityPostEntity p WHERE p.postId = :postId")
Optional<CommunityPostEntity> findByIdWithLock(@Param("postId") Long postId);
```

### 기대 효과
- ✅ 정합성: 락으로 데이터 보호
- ✅ 동시성: 순차 처리로 Race Condition 방지

### 실제 결과
- ❌ **데드락 발생**: FK 제약조건으로 인한 S-LOCK → X-LOCK 업그레이드 충돌
- ❌ **성능 저하**: 락 경합으로 인한 응답 지연

```
문제: 정합성과 동시성을 얻었지만, 데드락과 성능 저하 발생
```

## 시도 2: JPQL Atomic Update

### 접근 방식
```java
@Modifying
@Query("UPDATE CommunityPostEntity p SET p.likeCount = p.likeCount + :delta WHERE p.postId = :postId")
int updateLikeCount(@Param("postId") Long postId, @Param("delta") int delta);
```

### 기대 효과
- ✅ 동시성: Atomic 연산으로 Race Condition 방지
- ✅ 데드락 방지: S-LOCK 없이 바로 X-LOCK 획득

### 실제 결과
- ✅ 데드락 해결
- ⚠️ **성능 한계**: 모든 연산이 DB에 직접 쿼리됨
- ⚠️ **확장성 한계**: 트래픽 증가 시 DB가 병목

```
문제: 데드락은 해결했지만, DB 부하가 여전히 높음
```

## 시도 3: Redis 단순 캐싱

### 접근 방식
```java
// 조회수 증가
redisTemplate.opsForValue().increment("post:" + postId + ":viewCount");
```

### 기대 효과
- ✅ 성능: 메모리 기반 빠른 처리

### 실제 결과
- ⚠️ **Race Condition 가능성**: 읽기-수정-쓰기 사이에 다른 요청 개입
- ❌ **정합성 문제**: 서버 재시작 시 데이터 유실
- ❌ **좋아요 토글 문제**: SISMEMBER → SADD/SREM 사이에 중복 발생 가능

```java
// 문제가 되는 코드
if (!redisTemplate.opsForSet().isMember(key, userId)) {  // 1. 확인
    // ← 이 사이에 다른 요청이 끼어들 수 있음!
    redisTemplate.opsForSet().add(key, userId);           // 2. 추가
    redisTemplate.opsForValue().increment(countKey);      // 3. 카운트 증가
}
```

```
문제: 성능은 좋지만, 동시성과 정합성이 깨질 수 있음
```

## 최종 해결책: Lua Script + Write-Behind 패턴

### 핵심 아이디어

1. **Lua Script**: 여러 Redis 명령어를 **원자적으로** 실행
2. **Write-Behind**: Redis 데이터를 **주기적으로** DB에 동기화

### Lua Script로 동시성 해결

```lua
-- 좋아요 토글 Lua Script
if redis.call('EXISTS', KEYS[2]) == 0 then
  return -1  -- Cache Miss
end
local isMember = redis.call('SISMEMBER', KEYS[1], ARGV[1])
if isMember == 1 then
  redis.call('SREM', KEYS[1], ARGV[1])
  redis.call('DECR', KEYS[2])
  return 0  -- 좋아요 취소
else
  redis.call('SADD', KEYS[1], ARGV[1])
  redis.call('INCR', KEYS[2])
  return 1  -- 좋아요 추가
end
```

**왜 Lua Script가 안전한가?**

| 일반 Redis 명령어 | Lua Script |
|------------------|------------|
| 명령어 사이에 다른 클라이언트 개입 가능 | 스크립트 전체가 원자적 실행 |
| Race Condition 발생 가능 | Race Condition 불가능 |
| 여러 번의 네트워크 왕복 | 한 번의 네트워크 왕복 |

### Write-Behind로 정합성 해결

```
[실시간 처리]                    [배치 동기화]
    │                               │
    ▼                               ▼
┌─────────┐                   ┌─────────────┐
│  Redis  │ ──(5분마다)────▶  │   MySQL     │
│ (캐시)  │                   │ (영구저장)   │
└─────────┘                   └─────────────┘
    │
    ├── post:1:viewCount
    ├── post:1:likeCount
    ├── post:1:likes (Set)
    └── post:like:events (Queue)
```

**Event Queue를 통한 좋아요 관계 동기화:**

```java
// 좋아요 토글 시 이벤트 큐에 적재
redisService.addPostLikeEvent(postId, userId, isAdded);

// 스케줄러에서 배치 처리
@Scheduled(fixedDelay = 300000)  // 5분
public void syncPostLikeEvents() {
    List<LikeEvent> events = redisService.pollPostLikeEvents(1000);

    // 중복 제거 (같은 사용자가 여러 번 토글한 경우 마지막 상태만)
    Map<String, LikeEvent> deduplicated = events.stream()
        .collect(Collectors.toMap(
            e -> e.targetId() + ":" + e.userId(),
            e -> e,
            (old, new_) -> new_
        ));

    // DB 동기화
    deduplicated.values().forEach(event -> {
        if (event.isAdd()) {
            postLikeRepository.insertPostLike(event.targetId(), event.userId());
        } else {
            postLikeRepository.deleteByPostIdAndUserId(event.targetId(), event.userId());
        }
    });
}
```

## 최종 아키텍처의 트레이드오프 분석

### 달성한 것

| 요구사항 | 달성 방법 | 결과 |
|---------|----------|------|
| 정합성 | Write-Behind + Event Queue | ✅ (최종 일관성) |
| 동시성 | Lua Script 원자적 연산 | ✅ |
| 성능 | Redis 메모리 처리 | ✅ |

### 남은 트레이드오프

| 항목 | 상황 | 대응 |
|------|------|------|
| 최종 일관성 | Redis-DB 사이 최대 5분 지연 | 대부분의 서비스에서 허용 가능 |
| Redis 장애 | 데이터 유실 가능 | Redis Cluster, AOF 영속화 |
| 복잡성 증가 | 시스템 구조 복잡해짐 | 명확한 문서화, 모니터링 |

## 교훈: 정답은 없다, 상황에 맞는 선택이 있을 뿐

### 서비스 특성에 따른 선택

| 서비스 특성 | 권장 방식 |
|------------|----------|
| 트래픽 낮음, 정합성 중요 | DB 직접 처리 (JPQL Atomic) |
| 트래픽 높음, 실시간 중요 | Redis + Lua Script |
| 금융/결제 등 강한 정합성 | 분산 락 + 트랜잭션 |

### 우리의 선택 이유

커뮤니티 게시판의 조회수/좋아요는:
- 실시간 정확성보다 **사용자 체감 속도**가 중요
- 약간의 지연(최대 5분)은 **허용 가능**
- 높은 트래픽에서도 **안정적인 응답**이 필요

따라서 **Redis + Lua Script + Write-Behind** 패턴이 최적이었습니다.

## 마무리하며

카운터라는 단순해 보이는 기능에서 **정합성**, **동시성**, **성능**이라는 세 가지 요구사항을 동시에 만족시키는 것이 얼마나 어려운지 직접 경험했습니다.

**핵심 교훈:**

1. **트레이드오프를 인식**하라: 모든 것을 완벽히 만족시키는 해결책은 없다
2. **서비스 특성을 파악**하라: 무엇이 가장 중요한지 우선순위를 정하라
3. **점진적으로 개선**하라: 한 번에 완벽한 설계보다 반복적인 개선이 효과적이다
4. **측정하고 검증**하라: 추측이 아닌 데이터로 의사결정하라

카운터 하나에도 이렇게 많은 고민이 필요하다는 것, 그리고 그 과정에서 배운 것들이 다른 영역에도 적용될 수 있다는 것이 이번 경험의 가장 큰 수확이었습니다.
